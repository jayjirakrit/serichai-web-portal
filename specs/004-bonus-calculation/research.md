# Phase 0 Research: Bonus Calculation

All unknowns from the Technical Context are resolved below; none carried into Phase 1 as `NEEDS CLARIFICATION`. Verified directly against the real reference files at the repo root (`backend/.venv/Scripts/python.exe` + `openpyxl`, `data_only=True`) rather than taken only from the decompiled-VBA business-logic brief, since the brief itself invites verification.

## 1. One combined endpoint, matching `specs/001`/`specs/003`'s existing pattern

- **Decision**: A single `POST /accounts/bonus-calculation` uploads both files, computes every employee's results, and returns a summary, the flagged-employee subset (for on-screen review), and a downloadable `.xlsx` report `FileAttachment` with every employee's full detail — one call, one response, matching `CalculateBenefitsResponse`/`ReconcilePayrollResponse`'s existing shape exactly. (Further refined by spec Clarifications 2026-08-23 (3): the JSON response's per-employee detail is limited to flagged exceptions only, under `flaggedEmployees`, matching `ReconcilePayrollResponse.discrepancies` exactly rather than returning every employee individually on the wire — full per-employee detail lives only in the report.)
- **Rationale**: Superseded by spec Clarifications (2026-08-23 (2)): approved-day entry and final-bonus calculation happen *inside the generated report itself*, as a spreadsheet formula the user fills in after downloading — not as an in-app edit-and-recalculate step. That was the only reason an earlier version of this design split the flow into two calls (see prior revision of this decision, preserved in git history) — once finalization moved out of the app entirely, the second call had nothing left to do that the first call's report generation didn't already cover. This also removes the need for the frontend to hold any run state between calculate and download (no more "the frontend is the only place a partially-finalized run lives" — `data-model.md`'s Storage note simplifies to "nothing to hold, one call does everything").
- **Alternatives considered**: Keeping the two-call split "for consistency with the original design" — rejected, it would carry a `bonus-report` endpoint whose only remaining job is re-serving a file the first call could have produced directly, adding a network round trip and a duplicate set of request/response models for zero remaining benefit (Anti-Bloat, Principle V). A server-side run ID + in-memory store, to support some hypothetical future in-app re-download — rejected as speculative; nothing in the current spec calls for it.

## 2. Parsing approach: flat one-row-per-employee sheets (no department sections)

- **Decision**: All four source sheets (`ผลประเมินปี_<YY>`, `วันทำงานปี_<YY>`, `วันลาปี_<YY>`, `ผลสรุปโบนัสปี_<YY>`) are flat — one row per employee starting at row 5 (1-based; row 4 is the header, rows 1-3 are title/company text), no department-header rows interleaved the way `specs/003`'s payroll sheet has. Confirmed directly: `วันทำงานปี_68` rows 5/6 are two different employees back-to-back, not a section header + employee pair. So this feature's ingestion is simpler than `specs/003`'s: `pd.read_excel(sheet_name=..., header=None, engine="openpyxl")` → take row index 3 (0-based) as header, data from index 4 on, filter to rows with a non-blank first-name cell (mirrors `accounts_service.read_table`'s `dropna(how="all")` / blank-row filtering) — no `ffill()`/section-boundary logic needed.
- **Rationale**: Matches the actual file layout; adding department-section detection machinery here (copied from `specs/003`) would be speculative complexity the data doesn't need (Anti-Bloat).
- **Alternatives considered**: Reusing `specs/003`'s structural department-header detection unconditionally — rejected once the real files showed no such rows exist in this feature's inputs.

## 3. Column positions (verified against real files, 1-based)

- `วันทำงานปี_<YY>` (working days/OT, header row 4, data from row 5): col2 `คำนำหน้า` (prefix), col3 `ชื่อ` (first name), col4 `สกุล` (last name), col5 `อัตราค่าจ้าง` (pay rate), col6 `เริ่มทำงาน` (start date), col7 `หมายเหตุ` (department/notes — `"ออฟฟิศ"` marks office staff), col45 `รวมวันทำงาน` (WorkDays), col46 `รวม OT` (TotalOT), col47 `รวมวันหยุด` (TotalNotWorks), col48 `แผน (สูตรที่ใช้)` (OT-category code: `OT` / `OT SEWING` / `OT PAINT`). This is the **base sheet** — every other source is left-joined onto it by name.
- `วันลาปี_<YY>` (leave, header row 4, data from row 5): col78 sick, col79 personal, col80 special-personal, col81 absent, col82 vacation (accumulated annual totals); col83 (late minutes) exists but is unused, matching the business-logic brief exactly.
- `ผลประเมินปี_<YY>` (evaluation, header row 4, data from row 5): col2/3/4 prefix/first/last name (same convention); cols 5-17 (`E:Q`) are up to 13 per-criterion/evaluator numeric cells, averaged ignoring blanks into the numeric grade.
- `ผลสรุปโบนัสปี_<prevYY>` (previous-year summary, header row 5 in the real `สรุปโบนัส_68.xlsx` — one row lower than the other three sheets — data from row 6): col1 seq, col2 prefix, col3 first name, col4 last name, col5 pay rate, col6 start date, col7 department/notes, col8 work days, col9 total OT, col10 total-not-worked, **col11 = that sheet's own current-year letter grade** (labelled `grade{YY}` in the real file, e.g. `grade67` in the `_67` sheet — this is exactly what the *next* year's run reads as "previous grade"), col12 = that sheet's own previous-year grade (not used by this feature), col13 numeric grade, cols14-18 raw leave days, cols19-25 the 6 score columns + total score, col26 provisional days, col27 provisional bonus, col28 approved days, **col29 = that sheet's own final bonus** (labelled `Bonus ที่ได้` — this is what the *next* year's run reads as "previous bonus"), col30 = that sheet's own previous-year bonus (not used), col31 exception note. Confirmed by dumping `สรุปโบนัส_68.xlsx`'s `ผลสรุปโบนัสปี_67` sheet directly — its real header row and one real data row are the authoritative source for both this column mapping and this feature's own output-report column order (§7).
- **Rationale for citing exact positions**: the business-logic brief already gave these (decompiled from VBA); this section is the independent verification against the real files, which also resolved one ambiguity the brief's paraphrase left open — see §4.

## 4. Resolving "previous grade (col 11)" / "previous bonus (col 29)"

- **Decision**: Confirmed via the real file that col 11 and col 29 refer to the *previous-year sheet's own* current-year grade and final bonus (not a distinct "prior comparison" field) — i.e. this feature reads next year's inputs from exactly the columns the previous year's own run wrote its own results into. This closes a loop: each year's `ผลสรุปโบนัสปี_<YY>` output is next year's `ผลสรุปโบนัสปี_<YY>` input.
- **Rationale**: Confirms `data-model.md`'s `previousGrade`/`previousBonus` fields have an unambiguous source, and confirms the generated report (§7) should preserve this same column layout so the tool's own output file can, unmodified, serve as next year's previous-year-summary upload — preserving the feature's year-over-year workflow without any extra "export for next year" step.

## 5. Year input and sheet-name resolution

- **Decision**: The frontend collects a plain Gregorian year (e.g. `2025`, a number input defaulting to the current year); the backend derives `currentBeYear = year + 543` and `previousBeYear = currentBeYear - 1`, then builds sheet-name tokens: `ผลประเมินปี_{currentBeYear % 100:02d}`, `วันทำงานปี_{currentBeYear % 100:02d}`, `วันลาปี_{currentBeYear % 100:02d}` (looked up in `currentYearFile`), and `ผลสรุปโบนัสปี_{previousBeYear % 100:02d}` (looked up in `previousYearSummaryFile`). Mirrors `specs/003` Decision #3's Gregorian-input → BE-sheet-token pattern, and matches this repo's existing BE convention (`CLAUDE.md`: BE = Gregorian + 543).
- **Rationale**: Consistent UX with the payroll-reconcile period picker and the benefits feature's BE-year handling; keeps sheet-naming byte-for-byte identical to what the legacy macro (and this feature's own generated report, closing the loop from §4) produces.
- **Alternatives considered**: Asking for a raw BE year or the literal sheet-name token — rejected, leaks an internal convention to users who think in Gregorian years.

## 6. Employee matching, duplicate names, and the future `employeeId` seam

- **Decision**: `matchKey` = trimmed `firstName + " " + lastName` (whitespace-collapsed), computed once per row on every sheet. The working-day sheet is the base population; evaluation, leave, and previous-year data are left-joined onto it by `matchKey`. `EmployeeBonusRecord` carries both `matchKey` (the join key actually used in v1) and an always-`null`-in-v1 `employeeId: str | None` field — so a future feature can start populating `employeeId` upstream and switch the join key without changing the response shape (spec Clarifications, FR-004's forward-compatibility requirement). If a `matchKey` collides — appears more than once in the base sheet, or more than once in whichever source sheet is being joined against — that join is treated as unsafe: every base row sharing the colliding key gets a `duplicateName` exception and the ambiguous source's data is treated as not-found for them (never silently merged/misattributed, per spec Edge Cases).
- **Rationale**: FR-004 explicitly requires the matching approach to support an identifier-based join later "without a redesign" — a dedicated (if unused) field is the smallest change that satisfies this now. Treating any name collision, in any sheet being joined, as unsafe rather than picking "the first match" avoids silently attributing one employee's evaluation/leave/bonus data to a different employee of the same name.
- **Alternatives considered**: Using `firstName`+`lastName` as two separate join keys (no combined `matchKey`) — rejected, marginally more error-prone to normalize consistently across four call sites for no benefit. Silently taking the first match on a name collision — rejected, directly contradicts the Edge Case ("must not silently merge or misattribute").

## 7. Fixed scoring rules as backend constants

- **Decision**: All six rule sets (working-days bands, three OT bands, four leave-deduction formulas, and the 12-tier numeric→letter grade table) are module-level Python constants in `backend/services/bonus_service.py`, in the same style as `accounts_service.py`'s `SEVERANCE_MONTHS_TABLE`/`SURVIVAL_PROBABILITY_TABLE` — ascending `(lower_bound, value)` breakpoint lists consumed by the same `_bracket_lookup`-style helper (approximate/`VLOOKUP TRUE` match), reimplemented locally since `accounts_service.py`'s version is a private module function, not a shared utility. Grade lookup reuses the identical pattern: ascending `(numeric_lower_bound, letter)` pairs from `F` (below 2) up to `A` (12).
- **Rationale**: FR-016 requires a fixed rule set "mirrored from the legacy macro's tables," and spec.md explicitly defers editable/API-backed configuration to a future feature — module constants are the simplest thing that satisfies v1 while keeping the door open for a future config-driven version to replace just this one module's internals without touching the request/response contract (Anti-Bloat: no premature config-loading abstraction).
- **Alternatives considered**: A `backend/data/bonus_rules.json` file loaded at import time — rejected as unnecessary indirection for values that are fixed for this feature and not meant to be hand-edited (that capability is explicitly the deferred Configuration tab); a separate `bonus_rules.py` module — considered, but `accounts_service.py`'s existing convention keeps rule tables inline in the one service file that uses them, so this follows that precedent rather than introducing a new split.

## 8. When a missing/invalid input blocks `totalScore` vs. defaults to zero

- **Decision**: Verified against the real `ผลสรุปโบนัสปี_67` example row (employee flagged `ไม่เจอในวันลา`, i.e. `leaveNotFound`): that employee's four raw leave columns and four leave-score columns are all blank, **but `totalScore` (9.5) is still fully populated** as `grade(12) + workingDaysScore(-0.5) + otScore(-2)` — i.e. the legacy macro treats each missing leave-score component as a zero contribution to the sum, not as a blocking condition. Extending this one confirmed data point into a full rule, cross-checked against spec.md's Edge Cases wording:
  - `leaveNotFound` and `previousBonusNotFound` — **do not block** `totalScore`/`provisionalDays`/`provisionalBonus`. Leave-score fields are left `null` (not `0`) for display so the UI never implies "no leave was taken," while the sum treats the missing contribution as zero, matching the verified real row. `previousBonusNotFound` never affected scoring in the first place — it's comparison-only (FR-009, User Story 3 AC2).
  - `evaluationNotFound`, `evaluationAllBlank`, `otCategoryUnrecognized`, `duplicateName` — **do block** `totalScore`/`provisionalDays`/`provisionalBonus` (left `null`). Grade and OT-rule-selection are not optional additive components the way a leave category is — spec.md's Edge Cases are explicit that a blank-evaluation employee "must be flagged as an exception rather than producing a misleading zero or default grade," and the same reasoning extends to an OT category the system cannot look up a rule for (FR-006) and to a duplicate name (where evaluation/leave data can't be safely joined at all, so grade is unknown by construction).
  - A base (working-day sheet) row whose `payRate` cannot be parsed as a positive number gets a `workingDayDataInvalid` exception and is likewise blocked — provisional/final bonus math is meaningless without a rate. This one category has no direct precedent in the decompiled brief; it's added defensively since a garbled rate is a data problem, not a "component legitimately missing" case, consistent with the spirit of FR-003/Edge Cases.
- **Rationale**: This is the one place the decompiled-VBA brief's paraphrase ("the run still completes... flags... rather than a hard failure") left the exact per-category blocking behavior ambiguous; the real output file resolves it for the leave case conclusively, and the same logic extends cleanly to the other categories via spec.md's own wording rather than guesswork.
- **Alternatives considered**: Blocking `totalScore` for every exception category uniformly (simpler code, but contradicted by the verified leave-missing example) — rejected. Defaulting *every* category to zero including evaluation (matches nothing in spec.md, and directly contradicts the explicit "not a misleading zero or default grade" Edge Case) — rejected.

## 9. Report column layout (mirrors the real legacy output, closes the year-over-year loop)

- **Decision**: The generated report (now produced by `POST /accounts/bonus-calculation` directly, §1) reuses the exact 31-column order dumped from the real `ผลสรุปโบนัสปี_67` sheet (§3), with the two year-relative labels built dynamically from the request's `year` (e.g. `grade{YY}` using the *current* run's BE year, matching what the *next* year's run will read back as "previous grade" per §4). `employeeId` is included as a leading column even though it's always blank in v1, so a future run's export already has the column a real identifier would populate.
- **Rationale**: Preserves this feature's ability to feed its own output back in as next year's previous-year-summary file (§4) — the single most direct way to keep parity with the legacy macro's actual year-over-year usage pattern, not just its formulas.
- **Alternatives considered**: A new, cleaner column set unconstrained by the legacy layout — rejected; it would break the feed-forward loop and give finance staff a report shaped differently from the file they already know.

## 10. Approved-days/final-bonus columns as a live formula, not precomputed values

- **Decision**: Every other value column in the report (through `provisionalBonus`) is written by `openpyxl` as a static value at generation time. The approved-days column (`วัน`) is written as a genuinely blank cell — no value, no formula. The final-bonus column (`Bonus ที่ได้`) is written as an actual spreadsheet formula referencing that row's approved-days cell and `provisionalBonus` cell, e.g. `=IF(OR(AA5="",AB5=""),"",ROUND(AB5*AA5/30,0))` (column letters illustrative), so it recalculates the moment the user types a value into the approved-days cell — reproducing the legacy macro's own behavior (its `AB` column is deliberately left blank for HR to fill in, and its `AC` column is a live formula, per the decompiled-VBA business-logic brief this feature was specified from) rather than something this feature invented.
- **Rationale**: This is what makes User Story 2 ("...calculates automatically from the entered value... with no further action needed in the web application", FR-012) true without any backend involvement after the file is downloaded — there is nothing left to compute server-side once the file leaves the response. It also gives blocked-exception rows correct behavior for free (§8, FR-013): if `provisionalBonus`'s cell is blank, the `OR(...)` condition keeps the formula result blank no matter what's typed into the approved-days cell, with no separate per-row blocking logic needed inside the formula.
- **Alternatives considered**: Precomputing `finalBonus` server-side from a client-supplied `approvedDays` (the two-call design's approach, §1) — rejected along with the second endpoint. A macro/VBA-driven formula instead of a plain Excel formula (closer to the legacy file's actual implementation) — rejected as unnecessary; a plain formula produces the same recalculate-on-edit behavior without embedding VBA in a file this feature generates from Python, and doesn't raise Excel's "enable macros" security prompt for the user.

## 11. Correctness verification against known reference data

- **Decision**: Backend tests validate `bonus_service.py`'s scoring output against the same real, known-correct historical figures already used to derive and confirm the scoring rules and blocking/non-blocking behavior during this research phase (§3, §4, §8) — specifically, `สรุปโบนัส_68.xlsx`'s `ผลสรุปโบนัสปี_67` sheet (a completed, real prior run) as ground truth, cross-checking at least the flagged `leaveNotFound` example row (`ชิติมา กตัญญู`, §8) and a small set of additional rows spanning each OT-category table and at least one negative-`totalScore` case.
- **Rationale**: Matches the verification approach spec.md's Clarifications (2026-08-23 (2)) and Success Criteria (SC-003) now call for directly — reusing the reference data this feature was already specified and researched from, rather than commissioning a new independent ground truth, which would duplicate effort for no additional confidence (Anti-Bloat, Principle V).
- **Alternatives considered**: Building a synthetic, hand-crafted fixture with independently-derived expected values — rejected as strictly more work than reusing a real, already-verified historical run, and less convincing as evidence the implementation matches the legacy process's actual output.
