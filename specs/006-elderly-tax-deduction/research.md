# Phase 0 Research: Elderly-Employee Tax Deduction Service

All unknowns from the Technical Context are resolved below; none carried into Phase 1 as `NEEDS CLARIFICATION`.

## 1. Parsing approach: vectorized `pandas`/`numpy`, matching `accounts_service.py`

- **Decision**: Read both sheets with `pd.read_excel(io.BytesIO(content), sheet_name=..., header=None, engine="openpyxl")` into raw, position-indexed `DataFrame`s, then build typed vectorized columns on top — the same idiom `accounts_service.py` (`read_table`/`resolve_columns`) and `bonus_service.py` (`_read_flat_sheet`) already use, rather than per-row cell iteration. `openpyxl` (already in `requirements.txt`) is the only Excel dependency needed; no new library.
- **Rationale**: Both sheets are flat, one-row-per-employee tables (no department-section detection like `payroll_reconcile_service.py` needs) — a straightforward header-scan + vectorized-column pipeline is the simplest fit and keeps this the third Excel-ingesting service sharing one idiom.

## 2. Roster sheet (`ข้อมูลพนักงาน`) column mapping — positional, scan-for-`รวม`

- **Decision**: Row 1 is the header, data from row 2. The first 8 columns are name-resolved by scanning row 1 for their exact header text (ลำดับ, เลขบัตรประชาชน, คำนำหน้า, ชื่อ, สกุล, อัตราค่าแรง, วันเดือนปีเกิด, คนพิการ — the last ignored per spec). The 12 month blocks are **not** looked up by column letter; they're found by scanning row 1 left-to-right for every `รวม` header cell, in encounter order — the *n*-th `รวม` found is calendar month *n* (1st = ม.ค./January, ..., 12th = ธ.ค./December), per explicit implementation direction. Each block's wage/OT (and, for the 3rd and 12th `รวม` only, a preceding `โบนัส`) column are the cells immediately to the left of that `รวม`.
- **The รวม-parsing quirk (critical — a source of quiet bugs if missed)**: For 10 of the 12 months, `รวม` already equals wage + OT and can be read directly. For **March (3rd รวม) and December (12th รวม) only**, the source `รวม` cell includes that month's bonus column (`รวม = wage + OT + โบนัส`), because those two months' block has 4 columns instead of 3. The deduction-relevant monthly figure for every month must always be **wage + OT only, excluding bonus** (FR-003, FR-006 — "excluding bonus payments"). So the per-month reader must branch:
  - Non-bonus months (1,2,4,5,6,7,8,9,10,11): `monthly_net = รวม` column, read directly.
  - Bonus months (3, 12): `monthly_net = wage + OT` (the two columns immediately preceding `โบนัส`), **never** `รวม` directly, since `รวม` there also contains the bonus.
- **Rationale**: Verified against the real sample file `Tax_Reduction_Sample_filled.xlsx` (`ข้อมูลพนักงาน`, columns A:AT — 8 identity columns + 10×3 non-bonus blocks + 2×4 bonus blocks = 46 columns) — e.g. row 2's March block is `wage=14600, OT=139, โบนัส=7300, รวม=22039`; the deduction-relevant figure is `14600+139=14739`, not `22039`. Scanning for `รวม` positionally (rather than hardcoding absolute column letters) is also more robust to minor column-count drift between file revisions (see #3 below, where the two sheet layouts already disagree on column count in one variant found in the repo).
- **Populated vs. unpopulated month**: A month counts as "populated" for an employee when that month's **wage** cell is non-blank (not `NaN` after `pd.to_numeric(..., errors="coerce")`) — this is what distinguishes a genuinely unworked month (new hire not yet started) from a worked month with zero overtime. A populated month's blank/`NaN` OT cell is treated as `0`, not as missing data (confirmed against the template's placeholder rows, which have every month's wage populated but OT consistently blank/`None`).

## 3. Output sheet (`ผลประโยช์นพนักงาน`, exact spelling preserved) column mapping — name-resolved header scan

- **Decision**: Rows 1–3 are an untouched title block; row 4 is the header, data from row 5. Columns in the output template are resolved by scanning row 4 for their exact header text (ลำดับ, เลขบัตรประชาชน, คำนำหน้า, ชื่อ, นามสกุล, เงินเดือน, วันเดือนปีเกิด, อายุปัจจุบัน, then the 12 month-name headers ม.ค.–ธ.ค. in order, then รวม) rather than hardcoded column letters — a defensive header-scan even though the template is now a code-owned asset (`#6`, revised), so a future edit to the template's column order doesn't silently misalign writes.
- **Known discrepancy** (background for why `backend/data/Tax_Reduction_Template.xlsx` was set up the way it was): the root-level `Tax_Reduction_Template.xlsx` draft has a **20-column** `ผลประโยช์นพนักงาน` header (no `เลขบัตรประชาชน` column), while the verified ground-truth sample `Tax_Reduction_Sample_filled.xlsx` has a **21-column** header with `เลขบัตรประชาชน` as column B. `backend/data/Tax_Reduction_Template.xlsx` (the actual `TEMPLATE_PATH` this feature uses, per `#6` revised) was built to the 21-column ground-truth layout. Since `#6`'s revision stopped validating or reading the *uploaded* file's output sheet entirely, this discrepancy no longer matters for uploads — it only mattered for choosing which layout the static template itself should follow.

## 4. Buddhist-era DOB correction

- **Decision**: A stored `วันเดือนปีเกิด` value whose year is greater than the reference date's Gregorian year is recognized as Buddhist-Era-mislabeled and corrected by subtracting `BE_YEAR_OFFSET` (543): `corrected_year = raw_year - 543 if raw_year > reference_date.year else raw_year`. Implemented as a new `correct_be_year(dob, reference_date) -> date` helper in `backend/util/be_dates.py` (alongside the existing `retirement_date`/`benefit_year_end_date` helpers there), reused by `tax_deduction_service.py`.
- **Rationale**: A Buddhist-Era year is always Gregorian + 543, so a BE-mislabeled birth year is always numerically larger than *any* plausible past Gregorian birth year and — critically — always larger than the current/reference Gregorian year too (no one is born in the future), making `year > reference_date.year` a safe, simple discriminator with no false positives for real Gregorian birth years. Confirmed against the sample: raw DOB `2497-03-26` (2497 > 2026) corrects to `1954-03-26`; age at reference date 2026-09-18 computes to 72, matching the sample output sheet's `อายุปัจจุบัน = 72` exactly.
- **Alternatives considered**: A fixed cutoff year (e.g. "> 2400 is BE") — rejected as an arbitrary magic number that would eventually need updating; the relative-to-reference-date check needs no maintenance and is correct for any future reference date.

## 5. Partial-year averaging

- **Decision**: `average_monthly_net_salary = sum(monthly_net for populated months) / count(populated months)`, per spec.md Assumptions — never divided by 12 for an employee with fewer than 12 populated months. "Populated" uses the wage-cell-non-blank rule from #2.
- **Rationale**: Directly implements spec.md's documented assumption; matches the sample file exactly (`176147 / 12 = 14678.9166... → 14678.92`, the sample's own `เงินเดือน` value, for an employee populated in all 12 months).

## 6. Output workbook: static `TEMPLATE_PATH` template, not the uploaded workbook (revised)

- **Decision** (revised — supersedes an earlier draft of this research that filled the uploaded workbook's own bytes in place): `fill_output_workbook()` loads a static template, `backend/data/Tax_Reduction_Template.xlsx` (`TEMPLATE_PATH = DATA_DIR / "Tax_Reduction_Template.xlsx"`, `DATA_DIR` overridable via the `DATA_DIR` env var), exactly mirroring `accounts_service.py`'s `Employee_Benefit_Template.xlsx` and `bonus_service.py`'s `Bonus_Calculation_Template.xlsx` `TEMPLATE_PATH` pattern. The template is a single-sheet workbook (its own sheet name is renamed to `OUTPUT_SHEET_NAME`/`ผลประโยช์นพนักงาน` on load, matching `bonus_service.py`'s `ws.title = ...` convention) whose row 4 header already matches the 21-column ground-truth layout (`เลขบัตรประชาชน` included) and whose rows 1–3 carry a generic title block. Computed values are written into that template's data rows (row 5 onward, `5 + seq - 1`, one row per roster employee in original `ลำดับ` order) and the filled template is returned as the report — a **generated document**, not a copy of the caller's upload. The uploaded workbook's own `ผลประโยช์นพนักงาน` sheet (if it even has one) is never read, validated, or echoed back; only its `ข้อมูลพนักงาน` roster sheet is used, as input to the calculation only.
- **Rationale**: Explicit follow-up direction to use `backend/data/Tax_Reduction_Template.xlsx` as the output template and fill it, matching the `accounts_service.py`/`bonus_service.py` convention this feature had deliberately diverged from. This also resolves the #3 discrepancy note below for the *output* side entirely — a controlled, code-owned template can't drift from the ground-truth layout the way an arbitrary caller upload could, so `validate_output_sheet()` (formerly required to check an uploaded output sheet before writing into it) is removed as dead code; FR-011's malformed-upload rejection now rests entirely on `read_input()`'s roster-sheet validation.
- **Consequence for the request/response contract**: `payrollFile` no longer needs a well-formed `ผลประโยช์นพนักงาน` sheet at all — only `ข้อมูลพนักงาน`. The returned report always has a fixed filename (`OUTPUT_REPORT_FILENAME = "tax_deduction_report.xlsx"`), matching `bonus_service.py`'s `bonus_calculation_report.xlsx`/`accounts_service.py`'s `employee_benefits_report.xlsx` fixed-filename convention, rather than echoing the uploaded filename back.
- **Alternatives considered**: Keep filling the upload in place (the original decision) — rejected per explicit direction to match the other two services' static-template pattern instead.

## 7. One endpoint, one JSON+base64 envelope — matching the three precedent features exactly

- **Decision** (revised — supersedes an earlier draft of this research that split workbook/JSON into two separate endpoints): This feature exposes exactly one endpoint, `POST /accounts/tax-deduction`, returning one JSON envelope: `{ summary, employees, taxDeductionReport }`, where `taxDeductionReport` is the filled `.xlsx` embedded as a base64 `FileAttachment` (`backend/models/common.py`) — the identical shape `CalculateBonusResponse` (`bonus_report`) and `ReconcilePayrollResponse` (`reconciliation_report`) already use. `summary` carries both the run's headcount/eligibility figures and every rule constant applied (age threshold, salary cap, headcount percentage, BE offset, reference date), so FR-010's auditability requirement is satisfied by every response rather than a separate lookup call. `employees` carries the full per-employee breakdown (FR-009), and the browser decodes/downloads `taxDeductionReport` client-side (FR-008) — one request produces both outputs at once.
- **Rationale**: Explicit direction to consolidate to one endpoint "similar to other spec pattern" — the other three Excel-upload features in this backend (`employee-benefits`, `bonus-calculation`, `payroll-reconcile`) all follow exactly this one-request, summary+records+embedded-report shape; none of them expose a separate binary-download endpoint, a separate on-screen-JSON endpoint, or a separate constants-lookup endpoint. Matching this precedent exactly is more valuable for consistency than the raw-binary-response and no-base64-tax advantages a two-endpoint split would have offered.
- **Alternatives considered**: The originally-drafted two-endpoint split (raw-binary workbook download + separate JSON-only results endpoint) — rejected in favor of matching established precedent; a three-way split additionally exposing rules via `GET /accounts/tax-deduction-rules` — rejected for the same reason, folding the rule constants into `summary` instead (see #8).

## 8. Endpoint naming vs. Constitution Principle III (no verb suffixes) and the one-endpoint-per-resource-action precedent

- **Decision**: The originally suggested paths (`/api/v1/tax-deduction/calculate`, `/api/v1/tax-deduction/calculate-json`, `/api/v1/tax-deduction/rules`) are **not** used, because they violate Constitution Principle III's explicit rule against verb-suffixed endpoint paths (the same rule the constitution illustrates with `POST /accounts/employee-benefits`, not `.../employee_benefits/calculate`) and introduce a `/api/v1` prefix no other endpoint in this backend uses. Combined with #7's one-endpoint consolidation, a single resource-named, kebab-case endpoint extends the existing `/accounts` router: `POST /accounts/tax-deduction` — mirroring `bonus-calculation`/`payroll-reconcile`/`employee-benefits` exactly (one noun, one POST, no verb suffix, no separate GET for constants).
- **Rationale**: Constitution compliance is non-negotiable (Principle III); consolidating to one endpoint (#7) removes any need for multiple distinct nouns (`-workbook`/`-results`/`-rules`) in the first place.

## 9. Malformed-upload status code: 400 (domain validation) vs. 422 (request shape)

- **Decision**: A structurally malformed *workbook* (missing the roster sheet, missing an expected roster column) is raised as a new `TaxDeductionRequestError` in the service layer and translated to **400** by the router — matching `BenefitsRequestError`/`BonusRequestError`/`PayrollReconcileRequestError`'s existing precedent exactly, for consistency across the four Excel-upload features in this backend (all four now share the same "one POST endpoint, `XxxRequestError` → `HTTPException(400)`" shape end to end). FastAPI/Pydantic's own automatic request-validation errors (e.g. the required multipart field entirely missing, or an unparseable `referenceDate` string) already return **422** with zero extra code, per FastAPI's default behavior.
- **Rationale**: The original feature description's "reject malformed uploads with 422" is satisfied by FastAPI's built-in behavior for malformed *requests*; using 400 for malformed *file content* keeps this feature consistent with the other three services' established convention rather than introducing a fourth, inconsistent error-status story.

## 10. Selection pipeline order and tie-break direction

- **Decision**: The calculation function computes, for every roster row (not just age-qualifying ones): age (via #4) and average monthly net salary (via #2/#5) — both vectorized, independent of each other, so every employee's age/salary is always available for FR-007's "still showing computed age and average salary" requirement, even for an employee who fails the age test outright. `eligible = (age > AGE_THRESHOLD) & (average_salary <= SALARY_CAP)` is one combined boolean column. Only *within* the eligible subset does ranking happen: sort by `average_salary` descending, ties broken by ascending `ลำดับ` (original sequence number) — lower/first-in-file sequence number wins a tie, chosen for reproducibility per the Edge Cases requirement and because it requires no additional data beyond what's already read. `headcount_cap = floor(total_roster_rows * HEADCOUNT_CAP_PERCENT)`, using every roster row as `total_roster_rows` (spec.md Assumptions), and the top `headcount_cap` eligible employees (by the above order) are `selected = true`; the rest of the eligible set is `selected = false` (but still `eligible = true`, per FR-005/FR-007's three-state distinction from FR-014).
- **Rationale**: Satisfies FR-004 (age gate is a hard AND-condition, never hardcoded as `>= 60`; both `AGE_THRESHOLD` and `SALARY_CAP` are named constants) and FR-007 (auditable age/salary even for non-eligible rows) simultaneously — the "filter age first" guidance is preserved as the *first* term of the eligibility boolean (nothing ineligible-by-age is ever ranked or selected), while the vectorized pipeline computes age/salary for the whole roster in one pass rather than literally dropping rows, since dropping would break FR-007's display requirement.

## 11. `GET /health`

- **Decision**: A new, trivial `GET /health` returning `{"status": "ok"}` is added directly in `backend/main.py` (no new router file, no `/accounts` prefix — it isn't an accounts-domain resource).
- **Rationale**: No health contract exists yet anywhere in the repo — `specs/005-docker-deployment/research.md` #7 deliberately relied on FastAPI's built-in `/docs` for the Compose healthcheck instead of adding one. This feature's spec explicitly asks for a `health` endpoint of its own (Input — confirming the API is reachable before trusting a calculation call), so it's added here rather than skipped; it is independent of the #7/#8 endpoint-consolidation decision and does not replace or change the existing Compose healthcheck in `docker-compose.yml`/`backend/Dockerfile`, which is out of scope for this feature.
