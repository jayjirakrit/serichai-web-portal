# Phase 0 Research: Payroll Reconciliation

All unknowns from the Technical Context are resolved below; none carried into Phase 1 as `NEEDS CLARIFICATION`.

## 1. Parsing approach: vectorized `pandas`/`numpy` vs. `openpyxl` cell scanning

- **Decision**: Parse the workbook with `pd.read_excel(header=None, engine="openpyxl")` into one raw `DataFrame` (positional integer columns, no header inferred), then build a typed, vectorized pipeline on top of it — the same idiom `backend/services/accounts_service.py` already uses for the employee master file (`read_table` → `resolve_columns` → a clean `DataFrame` → `pandas`/`numpy` vector operations), rather than the row-by-row cell scanning originally proposed. `pandas`'s `openpyxl` engine reads each cell's last-cached calculated value (not the formula string), the same effective behavior as the legacy batch's `FormulaEvaluator.evaluateInCell`.
- **Rationale**: The irregular parts of this layout (department header rows, two physical rows per employee) are boundary-*detection* problems, not row-*iteration* problems — they can be expressed as vectorized operations over the whole sheet at once: a boolean mask over one column finds every department-header row; `Series.ffill()` propagates each department label down over its section's data rows; a within-section running count (`groupby(...).cumcount()`) tags every row as the attendance row or the overtime row, replacing the Java loop's `rowIndex += 2` bookkeeping. Once tagged, the attendance rows and overtime rows are split into two frames and rejoined side-by-side (`pd.concat(..., axis=1)`) to get one row per employee — the vectorized equivalent of `mapToReport` reading `row` and `otRow` together. This matches the project's existing convention (only `accounts_service.py` currently ingests Excel, and it already does this) and lets the per-day-count columns (`getWorkingTime`'s `Map<Integer, BigDecimal>` + stream-reduce sum in Java) collapse to one `.iloc[:, start:end].sum(axis=1)` call instead of a manual loop-and-dict.
- **Alternatives considered**:
  - Cell-by-cell `openpyxl` scanning (the original Phase 0 decision) — reconsidered: works, but every feature ends up hand-rolling its own row-walking code instead of sharing one Excel-ingestion idiom across the backend; reverted in favor of consistency with `accounts_service.py` per explicit direction.
  - Re-implementing formula evaluation in Python — still rejected: unnecessary, `pandas`'s `openpyxl` backend already surfaces the cached calculated value.

## 2. Locating the header row and department sections (vectorized)

- **Decision**: Read the sheet's header row (index 2) as a plain list from the raw `DataFrame` and scan it in Python for the `วันหยุด` and `วันปกติ` marker cells — a single O(columns) scan, not a per-row operation — then derive every other column position as a fixed integer offset from `วันปกติ`'s column, exactly as `ReportHeaderPosition`'s builder does (a small dict of `{field: column_index}`, computed once per request). Department-section and row-pairing detection over the *data* rows (the actual per-employee bulk of the sheet) is fully vectorized per Decision #1, but section-header detection is **structural, not name-based**: a row counts as a department-header row when its department cell is non-blank *and* its employee first-name cell is blank (`is_dept_header = department.notna() & first_name_blank`), not by checking the department name against `KNOWN_DEPARTMENTS`. `department.where(is_dept_header).ffill()` then broadcasts each section's raw name down to its data rows, and a within-section `cumcount() % 2` assigns each data row's attendance/overtime role within its pair (a section is cut off at the first attendance-position row whose index cell is blank, mirroring the legacy batch's own per-pair termination check).
- **Rationale**: The header-marker scan is inherently a small, one-time lookup (a few dozen cells, not thousands of rows) — porting `getHeader`'s logic there as plain Python is clearer than forcing it through `pandas`, while the actual per-row bulk work (section boundaries, row pairing, sums, formulas, comparison) gets the vectorization, which is where it matters for both clarity and the 1,000-row performance goal (SC-004). Detecting section headers by name (`isin(KNOWN_DEPARTMENTS)`) was tried first but rejected during implementation: a department whose name isn't one of the four known categories would then fail to be recognized as its *own* section at all, and its employees would silently merge into whichever recognized section precedes them in the sheet — directly violating FR-013 ("flagged as an exception needing review rather than silently skipped"). The structural blank-first-name check works regardless of what the department cell says, so an unrecognized name still opens its own section and every employee under it is correctly reported as `unrecognizedDepartment` (Decision #5) instead of being mis-attributed to a different department.
- **Alternatives considered**: Requiring a stricter, purpose-built template for uploads — rejected; the spec's stated intent is feature parity with the existing batch, and finance already produces files in this exact layout. Name-based section-header detection (`isin(KNOWN_DEPARTMENTS)`, the original Phase 0 decision) — reconsidered and replaced with the structural check above once the FR-013 conflict was found.

## 3. Period input and sheet-name resolution

- **Decision**: The frontend collects a period as a month/year value (`YYYY-MM`, e.g. via an HTML `<input type="month">`); the backend converts it to the workbook's exact sheet-name token, `ประจำ {M-yy}` (Gregorian month with no leading zero, two-digit **Buddhist Era** year — BE = Gregorian year + 543 — e.g. `2026-08` → `ประจำ 8-69`). The legacy batch's `sheetDate` (`M-yy`) is derived from a `batchDate` argument whose year component is already BE-numbered (it's fed straight into `java.time.LocalDate`, which performs no calendar conversion — it just echoes back whatever year digits it was given), so the `yy` token it produces is a BE year, not a Gregorian one. Confirmed against real finance workbooks: `ช69-1.xlsx`/`ช69-4.xlsx` (named `ช{BE yy}-{M}`) contain sheets `ประจำ 1-69`/`ประจำ 4-69` for January/April 2026 (2026 + 543 = 2569 → `69`), not `ประจำ 1-26`/`ประจำ 4-26`.
- **Rationale**: Keeps the sheet-naming convention byte-for-byte identical to the file finance already produces, while giving portal users a normal date picker instead of asking them to know or type the raw Thai sheet name.
- **Alternatives considered**:
  - Free-text sheet-name field — rejected: leaks an internal naming convention to end users and invites typos.
  - Auto-detect the workbook's only sheet — rejected: spec.md's Assumptions explicitly allow a file to contain multiple period sheets (one per month), so a period selector is required.

## 4. Discrepancy detection semantics (vectorized across the whole sheet)

- **Decision**: Recalculate `actualTotalWage` for every employee in one pass using `pandas`/`numpy` column arithmetic: build the two department formulas (office: salary-based with `/30` daily divisor; metal-shop/sewing-shop/contract: per-day-count based with `/8` hourly divisor for overtime — both ported unchanged from `CalculationReconcileService`) as two full-column `Series` computed over the whole employee table, then select per row with `np.where(is_office, office_formula, other_formula)` — the vectorized equivalent of the Java `if (OFFICE_DEPARTMENT.equals(departmentName))` branch, mirroring how `accounts_service.py`'s `liability_at_year_end` already picks between branches with `np.where`. The conditional social-security calculation (skipped when the source row's stated social security is already zero) is likewise a `np.where(stated_social_security == 0, 0, bracket_lookup(...))` column. Compare the recalculated column to the stated `actualTotalWage` column with both half-up-rounded to 2 decimals (Decision #4a); any row where they differ is a discrepancy — one boolean mask over the whole table, not a per-row Python loop.
- **Rationale**: Byte-for-byte parity with the legacy batch's comparison is required by spec SC-002 ("100% of wage discrepancies that the legacy nightly batch process would have flagged are also flagged by this feature"). Doing it as whole-column arithmetic instead of a per-employee loop is both the established style in this backend (`accounts_service.py` has no per-row Python loop for its formula either) and comfortably meets the 1,000-row / 30-second performance goal (SC-004).
- **Alternatives considered**: A tolerance-based comparison (e.g. within 0.01 baht) — rejected; the legacy batch uses exact equality after rounding, and introducing a tolerance would silently hide discrepancies the batch would have caught, violating SC-002. A per-row Python loop (the original Phase 0 decision, ported straight from Java) — reconsidered in favor of vectorized column arithmetic per explicit direction to match `accounts_service.py`'s idiom.

## 4a. Matching Java's `RoundingMode.HALF_UP` in `pandas`/`numpy`

- **Decision**: `RoundingMode.HALF_UP` always rounds a tie (`x.xx5`) away from zero; `numpy`/`pandas`'s default `.round()` is round-half-to-even (banker's rounding) and will silently disagree with Java on exact `.xx5` values. Since every wage amount here is non-negative, use a small vectorized helper — `np.floor(series * 100 + 0.5) / 100` — applied to both the recalculated and stated wage columns before comparing, instead of a bare `.round(2)`.
- **Rationale**: A rounding-mode mismatch would make this feature disagree with the legacy batch on the rare `.xx5` boundary case, which is exactly the kind of silent parity gap SC-002 exists to prevent. This is cheap to get right up front and easy to miss later, so it's called out explicitly rather than left implicit in the formula code.
- **Alternatives considered**: Python's `decimal.Decimal` with `ROUND_HALF_UP` per value — correct but reintroduces a per-row Python loop (`Decimal` doesn't vectorize over a `Series`), which Decision #4 specifically moved away from; the `numpy` expression gives the same result for this domain (non-negative currency amounts) without giving up vectorization.

## 5. Handling unrecognized departments and malformed rows

- **Decision**: A department-column value that isn't one of the four known names does not stop processing or get silently skipped — a boolean mask (`~department.isin(KNOWN_DEPARTMENTS)`) selects every employee under it in one pass and reports them as an `unrecognizedDepartment` exception (no wage recalculation attempted, since the formula to use is unknown). Rows whose paired OT row is missing or whose numeric cells fail to parse are found the same way — `pd.to_numeric(..., errors="coerce")` turns unparseable cells into `NaN`, and a mask over `.isna()` on the required numeric columns selects those employees for a `dataError` exception — rather than crashing the whole run or silently defaulting missing values to zero.
- **Rationale**: Directly implements spec.md's Edge Cases ("flagged as an exception needing review rather than silently skipped... or causing the whole run to fail" / "flagged as a data-error exception rather than silently producing a wrong calculation").
- **Alternatives considered**: Rejecting the whole file on any malformed section — rejected; too coarse, and defeats the purpose of surfacing *which* records need review.

## 6. Report generation and delivery

- **Decision**: Build two `openpyxl` workbooks in-memory and return both as base64-encoded `FileAttachment`s (reusing the exact pattern already established by `backend/models/benefits.py` / `EmployeeBenefits.tsx`'s `downloadFileAttachment`): a full reconciliation report (every employee processed, stated vs. recalculated amount, status) always present, and a discrepancies-only report present only when `discrepancyCount > 0` (`null` otherwise, per spec User Story 2 Acceptance Scenario 3 — "make clear there is nothing to download rather than producing a confusing empty file").
- **Rationale**: Reuses a UI/download pattern the user already knows from the Employee Benefits page instead of introducing a new interaction model; the legacy batch's summary-Excel column set (`#`, name, salary, hours worked, calculated vs. stated wage) is preserved so finance staff see familiar columns.
- **Alternatives considered**: Emailing the reports (legacy behavior) — explicitly out of scope per spec.md Assumptions; CSV instead of Excel — rejected, Excel matches both the legacy batch's output and the existing benefits feature's report format.
